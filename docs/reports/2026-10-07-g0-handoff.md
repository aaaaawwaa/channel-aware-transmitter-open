## 已定案的判断（不要重新论证）

- **F2 是"不可观测的区分"，不是缺陷。** `== RF_STATE_FAULT` 改成 `!= RF_STATE_READY` 能通过全部 399 条。我尝试构造反例失败：**任何"stop 后仍有活动"的情形都会让 gated setter 把 core 打成 FAULT**，于是两个判别式在所有可达路径上重合。守卫保留为显式意图。残余风险：若将来"非FAULT且有活动"变得可达，该限制将变成未测的承重条件。证据 `f2-test-green.log`。
- **daemon 版本必须与 minor 同步升到 1.0.3**：`scripts/rf_environment_candidate.py` 的硬编码配对表 `{'1.0.1':3,'1.0.2':4,'1.0.3':5}` 与 `rf_daemon_main.c` 的 manifest 校验都要求，不升版则新候选会被发布工具拒绝。
- **`rf_core_safe_shutdown` 结尾无条件置 `OFFLINE`**，所以它**不能**用于"停器件但保留 FAULT 证据"——这就是新增 `rf_core_release_part_keep_state` 的原因。
- **不得在 `apply_disconnect_rule` 里按"观察到有活动"回退**：连续捕获（`RF_STATE_RX_CAPTURING`）也会留下活动，那是**另一个已知 core 级缺口**（`rf_core.c` 没有 `stop_rx`，注释明写 escalated separately, not patched here），必须继续如实报告"未确认"。我试过一次，破坏 5 条既有测试。

**坑（都真实踩过）**
- **加了新守卫之后，旧变异必须重跑。** 这是本工程最贵的一个坑，round-2 真发生过：`wait_campaign` 的"必须给 baseline"守卫是在拿到八帧上限的变异验证**之后**才加的，而它排在档位检查**之前**，于是那条变异悄悄失效——把档位检查整段删掉，49 条测试仍然全绿。独立审阅者用"删掉检查看是否还绿"抓到了。**判据：任何测试的 `pytest.raises` 都要 match 到它名字所指的那条特定消息**，否则一个更早的守卫就能满足它。
- **源码是 CRLF**：`perl -0pi -e 's/...\n/.../'` 会静默不匹配。用 Python `io.open(newline='')`，或 `\r\n`。
- **变异必须先断言"已生效"再编译**：我第一次做 F3 变异时模式没匹配，编译 exit=0、无 FAIL，读数看起来像"变异通过了"。要 grep 确认改动落地。
- **`fake_pl_set_read_failure(off, on)` 的 `off` 是小索引**（`read_fail[0x40]`），传 `RF_CTRL_A(...)` 会越界成空操作。
- **`fake_pl_set_capture_arm_stuck(1)`** 会让"清 CAP_ARM"写不生效 → gated setter **fault core**，所以不能用来构造"非FAULT且有活动"。
- **`timing_before_read` 钩子**（test_rf_daemon.c:63/71）：能在 **EOF 之前、连接仍存活时**于读边界执行检查；用法见 `test_a_failed_wait_stops_the_source_inside_the_transaction`。**`serve()` 返回后再检查分不清"交易内清理"与"断线清理"** —— 这正是 F1 的教训。
- **`test_selftest` 的两条 `FAIL` 是预期负控**（丢弃寄存器写 / 非AD9361），其后是 `SELFTEST HARNESS OK`。**不要把跨二进制的 PASS 行数当成某个二进制的结果**（`783/2` 就是这么误报的）。
- **`test_platform_rf.c` / `fake_pl.c` / 多数 board_app 源文件是 untracked**，无法做行级 diff 对比改动前。已冻结 round-2 快照到 `frozen-sources-round2/`，让下一轮能做**正文**差分（round-1 快照已不可恢复）。
- **`test_vendor_integrity.py` 是脚本不是 pytest 模块**：`python test/test_vendor_integrity.py`，用 pytest 跑会得到 `no tests ran`。
