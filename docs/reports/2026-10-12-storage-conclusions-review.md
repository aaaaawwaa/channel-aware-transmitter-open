# 存储与部署结论复核

**结论：存储的有限观测及真实研究租约阻断基本成立；“部署恢复机制已完整落地”不能批准。** 当前预检仍有实际放行缺口，自写FAT工具的检查范围也被报告说大了。可以继续离线修复，不能把320个既有测试通过等同真实研究或部署恢复条件全部满足。

审查输入为用户提供的session-98999ece日志包（809条事件）、当前源码及冻结证据。本次没有连接板卡、上传、安装、Overlay、RF操作，也没有修改生产代码。只核验关键部分，47项相关既有测试通过；另行执行三个离线反例和一次真实保存镜像重放。

## 关键发现

### P1：预检并未完全fail-closed

`scripts/rf_headroom_deploy.py` 的 `board_snapshot()` 有有效JSON时，即使远端退出码非零仍返回非空字典；调用端只用 `if not pre` 判断是否不可用。`SNAPSHOT` 内各命令的rc/err被丢弃，`kernel_storage`只保留stdout，因此内核日志不可读也可能成为空字符串，被当成没有故障。

本次使用原有真实bundle＋假板卡夹具独立复现：

| 注入缺陷 | 实际行为 |
|---|---|
| 快照返回有效JSON但退出码为1 | 上传3文件、派发安装1次，结局INSTALLED_VERIFIED |
| 快照缺少kernel_storage字段 | 上传3文件、派发安装1次，结局INSTALLED_VERIFIED |

这直接反驳“预检不可用→不上传不派发”的全面声明。原测试只覆盖整个快照为空，没有覆盖部分命令失败、字段缺失和非零退出码。应先保存并验证各项检查状态、必需字段及全程退出结果；禁止把不可读和无故障合并。最终复现从正确旧父发布开始，派发后假板卡转为新发布；收据 `preflight-findings-valid-parent.json`。

### P1：只完成观察会话分离，未完成独立远端执行

当前安装仍通过原SSH连接同步 `_run(...sh install.sh...)` 执行，之后关闭该连接，再创建只读观察连接。没有独立持久作业或远端attempt状态机保证安装进程脱离该SSH生命周期；因此不能保证观察超时/断连不会影响执行。

超时异常后还会先在原连接上打开SFTP下载状态文件，才进入关闭连接及新观察会话。这段再次依赖故障连接，缺少独立的有界状态下载设计。测试中的FakeSftp立即返回，没有覆盖真实会话创建卡住。

“只派发一次、无自动重装、追加本机attempt日志、新连接读回”属于有效改进，但不能替代上面两项。应把观察期限与实际执行生命周期分开，并让远端保存可独立读取的attempt/阶段/退出状态；不是简单延長240秒。

### P2：FAT审计不完整覆盖LFN序列

`scripts/fat_structure_audit.py` 的 `assemble_lfn()` 对序号排序，只检查至少一个末项标记和校验和，没有强制验证序号连续、唯一及末项标记的位置。

独立构造一个内容不变的FAT16镜像，把LFN最高序号改成重复的ordinal1并保留末项标记。当前工具仍判 **consistent、0 error、0 warning**。因此“所有LFN序列正确/完整结构审计”不成立。该反例不证明真实保存镜像有这个错误，只说明工具没有能力排除该错误。收据 `lfn-counterexample.json`。

## 可以接受的结论与必要边界

| 原结论 | 复核 |
|---|---|
| 分区是FAT16，130MiB、33241簇 | 成立；从原镜像BPB及簇数重新计算、重放一致 |
| 两次抓取字节相同 | 成立；两个gz完整解压后均为136314880字节、SHA256均0b809abc… |
| 七文件与备份相同 | 成立；重放7/7摘要及长度匹配 |
| 自写工具在已实现检查范围内未检出缺陷 | 成立；真实报告重放业务字段相同 |
| 本启动/观测窗口未见新存储错误 | 日志支持；不能推广到长期硬件健康或已定位MMC根因 |
| ext4 state=1、error_count=0 | 是超级块字段读回，不能替代根分区完整e2fsck |
| FAT挂载提示来自状态位 | Linux5.4源码支持；与此前SDHCI超时是两条不同的证据 |
| 当前HEADROOM生产链被lease_held阻止 | 成立，并且关闭路径也存在相同语义矛盾 |

还需收窄四种表述：

1. **两次镜像相同不能证明绝无并发写入。** 可以在两次读取之间写入后恢复，或写入相同内容；raw dd也是正在rw挂载的卷的顺序读取，不是原子快照。正确表述是“两次抓取未观察到内容差异，支持输入可重现”。
2. **与备份一致不能单独证明文件本来就是正确的。** 可证明备份保真/未发生相对于该备份的变化；备份取得于故障恢复后，不是独立已知正确的出厂镜像。成功启动与已验证发布是另外的正面证据。
3. **报告不是完全逐字段相同。** 原报告与重放报告的`path`、`utc`不同，其余业务字段相同。本次独立重放也仅规范这两个字段。
4. **只读检查不会清除脏标记。** 清除是写入行为，须另外经过备份、卸载和实际修复流程；不能把`fsck.fat -n`或只读chkdsk说成清除操作。

Linux5.4 `fat_set_state()` 在挂载时已脏的情况下打印该提示并提前返回，正常卸载也不能由该函数自动清掉这个已有标记。参见[官方Linux源码](https://raw.githubusercontent.com/torvalds/linux/v5.4/fs/fat/inode.c)。dosfstools4.1检查0x25状态位后，经选择修复会调用fs_write清除；参见[官方dosfstools源码](https://raw.githubusercontent.com/dosfstools/dosfstools/v4.1/src/boot.c)。这支持该提示的解释，不证明其一定由此次断电首次产生，也不能否认此前已捕获的MMC中断超时/ADMA故障。

## 租约阻断的推理成立，修复范围需扩大到收尾

真实 `rf_daemon_serve()` 在读取任何请求前取得连接租约，结束连接后才释放；`state.get`用同一`session.lease_held`字段报告状态。生产控制器在保留连接中读能力，而 `capability_available()` 要求这个字段为false，所以当前真实路径必拒。已有实板只读能力记录也确实是true，其他必要项均匹配。

另外 `RfStatusClient.headroom_closing_readback()` 与控制器 `_closing_confirmed()` 都要求同一连接读回 `lease_held=false`；即使只修入口，将来也会无法确认关闭。需要正确区分“本连接拥有控制租约”和“RF路径仍活动/另一控制方占用”，同时保留原生独占、预算及TX/RX关闭门禁。

此前G1模拟对端把lease_held置成false，未覆盖实际原生服务端的语义；这是此前验收漏测，不能用G1 PASS否认该缺陷。新资格应加入原生serve实际状态到生产Python的合同测试，不能仅再改一个假对端字段或放宽所有状态判据。

## 建议结论和次序

建议采用：“当前板卡在限定观测窗口内未再出现存储错误，保存启动镜像的已实现结构检查与七文件备份一致；SD/根分区完整健康及MMC根因未证明。部署日志和超时读回有进展，但预检错误传递和远端执行生命周期仍需补齐。当前研究租约判据存在确定的生产阻断，需覆盖入口和关闭路径修正后重新资格。”

下一步优先修预检失败传播及远端作业生命周期，再统一租约语义、补实际原生合同测试及新候选资格；真实研究仍保留一次初始化、最多五次、出错即停止的限制。无需因FAT挂载提示本身重训模型或重做整个既有接收链。
