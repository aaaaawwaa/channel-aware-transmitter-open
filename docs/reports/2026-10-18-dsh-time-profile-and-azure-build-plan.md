# DSH 调用耗时与 Azure 构建分工

检查日期：2026-10-18。用户确认可使用之前的 Azure 虚拟机，内存 16 GB。本次只分析本机日志、源码及历史记录，没有连接或改动虚拟机和板卡。

## 1. 结论

**工具和模型两边都要优化；把所有延迟归因于板端编译不符合日志。** 最近工作包的 agent 累计响应时间约一半是模型请求，一半是工具。主会话中的长工具调用大量是在等待子任务，不代表 CPU 一直在计算。

Azure 适合承担离线回归、隔离变异、C 原生测试和 ARM 交叉编译。它的最大价值还包括让板卡空出来进行有效的资格验证：本次新日志已出现第二次编译与 ARM 计时争用 CPU，使 P95 超标。

先消除重复计算与资源冲突，再迁移计算。减少细碎模型往返和超大上下文，同样重要。

## 4. 时间大头在哪里

### 长等待与测试/变异

近期找到 17 次显式等待/轮询 shell，累计约 103 分钟；常见形状是 14 次 `Start-Sleep 28/30` 并检查 NOTES 文件，单次持续约 391–422 秒。原始索引如：

- 主 `session.v4.jsonl:7198`：等待两个修复实例，393.8 秒。
- 主 `session.v4.jsonl:7343`：等待 P1/P2 完成，422.2 秒。
- 主 `session.v4.jsonl:7503`：等待第一会话产物，393.5 秒。

这些等待多数与子任务工作重叠，**不能全部视为浪费**。可优化的是不必要的轮询往返、对“报告是否写完”的依赖、等待期间无意义的重复 Git/目录扫描。优先使用 job/子任务完成事件或简洁结构化状态；不要为写完长 NOTES 才允许下一步读取已经生成的机器结果。

后台计算中，测试/变异是主要可迁移工作。近期可直接归类的已完成测试 job 至少累计约 119 分钟，另有自定义脚本未完全归类；该值包含并行，不能与 parent 等待相加。

## 5. Azure 可以复用什么

历史记录：

- `docs/superpowers/plans/2026-09-24-autodl-runner-bootstrap.md:5`：Azure fpga-runner，Ubuntu 22.04、Standard B4s v2、4 vCPU / 16 GiB。这是历史登记，当前配置还应只读核对。
- `docs/reports/2026-09-30-ac820-rf-phase2-progress.md` §4：该 Azure 已使用 **ubuntu:20.04 容器 + ARM hard-float 交叉工具链**成功构建并部署 ARM 32 位 daemon，记录的 GLIBC 需求 2.4/2.7/2.17 与板卡参考 ABI 相符。

因此“x86 虚拟机只能产生 x86，必须在板上编译”并不成立。项目构建脚本的现行板编译路径可以保留为回退；历史经过验证的交叉环境应优先检查复用。

### 推荐分工

| 本机 | Azure 16 GB | 板卡 |
|---|---|---|
| DSH 调度、源码快照、Windows GUI/串口测试、板卡连接中转 | Linux 可移植 Python 回归、C host 测试、隔离变异、ARM 交叉编译、打包与摘要 | ELF/加载兼容检查、真实 ARM 性能、受控试部署与读回、RF/触摸/真实采集 |

Azure 不需要能直接连接 192.0.2.10；若网络不通，可以“本机 → Azure 编译 → 本机取件 → 技能规定的板卡 helper 上传”。避免为了构建先搭公网板卡访问。

### 接入步骤

1. **只读盘点旧 VM**：CPU/内存/磁盘、现有容器镜像、工具链版本、sysroot、旧构建目录。先用已有环境，不重装 Vivado；本轮没有 PL 变化，不跑 bitstream。
2. **固定输入**：从 `final_prj` 导出准确提交及需要的补丁，核对摘要；云端独立 Linux 工作目录，不使用过期 signal_generator 工作树覆盖当前工程。
3. **先迁计算量大的离线套件**：相同快照先做一次本机/VM 对照；测试分片起步 2 个进程。对固定输出路径或会改源的测试保留隔离/串行，不直接全库 `-n auto`。pytest-xdist 支持进程数与文件分组调度。[pytest-xdist 官方文档](https://pytest-xdist.readthedocs.io/en/stable/distribution.html)
4. **增量构建与缓存**：已有 4 vCPU 配置可从 make -j2 或 -j4 对照起步；同一 agent 不同时启动多份全量测试。启用持久 ccache，缓存相同编译输入，避免每步 clean/全量编译。ccache 按编译输入复用结果。[ccache 官方手册](https://ccache.dev/manual/latest.html)
5. **交叉工具链与 ABI**：复用旧 ARM hard-float 环境，确认 ARMv7/ELF32/EABI、动态加载器、GLIBC 符号需求及必要依赖。明确 sysroot；它决定目标头文件和库的逻辑根目录。[GCC sysroot 说明](https://gcc.gnu.org/onlinedocs/gcc/Directory-Options.html)
6. **诚实接入产物验证**：构建收据明确 `build_host_arch=x86_64`、`target_arch=armv7l`、编译器/参数/sysroot、源码与产物摘要，区分 VM 上的 host tests 和板端运行。不得伪装成“板上 native 编译”。现有 verify_observer_build 的收据/schema 与日志要求若不支持，应一次适配并相关验证，不能捏造旧字段绕过。
7. **板卡独占**：构建、ARM 计时、部署和 RF 统一经过同一个执行者/资源互斥机制；预检之后也要持有任务级互斥，不能仅执行前扫描一次进程。当前已有正确候选只做必要的无竞争复验，不为云迁移重编。

历史 B4s v2 是可突发 CPU 机型。CPU credits 耗尽会降至基准性能，所以不能把“4 vCPU”视作任何长任务都持续满速；先查看 credits/CPU 使用，再决定并发，不需要先升级实例。[Microsoft Bsv2 说明](https://learn.microsoft.com/en-us/azure/virtual-machines/sizes/general-purpose/bsv2-series)

## 6. 优化顺序与收益验证

1. 当前马上避免板端编译与 ARM 资格并发，避免已正确产物再次重编；保留 413.6 ms 失败记录，按授权做一次低干扰资格复测。
2. 把长任务后台化、完成通知事件化；用机器结果驱动交接，不等长篇 NOTES 写完。
3. 相同源码 + 测试集合 + 环境结果复用；每次代码改动跑相关回归，一次整合后再跑必要整套，不让实现者、审查者和收口实例都重复全跑。
4. 模型读取与状态查询批量执行；主 agent 收到关键差分/失败摘要即可，不反复读整段历史。阶段切换给执行者短上下文、明确文件和完成条件。
5. 普通读写/日志摘要用较低推理强度，跨层根因和关键增量审查保留较高强度；按 DSH/提供方实际支持的设置操作，不推断仅提示一句就改变了模型参数。
6. 用旧 Azure 环境接入离线测试与后续交叉编译。迁移接入独立推进，不成为当前 33 帧工作的新前置长项目。

不承诺“整体快几倍”。先测同一快照的冷/热构建、相关测试/必要全套、传输与板端占用，分别保留 elapsed/user/sys、退出码、源码摘要。虚拟机不能缩短模型服务端响应，也不能替代板上实测；整体收益应在下一工作包按同一统计口径比较。
