# 个人开发审查与部署规则

生效日期：2026-10-17。依据用户本轮明确要求：个人、离线、有线板卡开发，减少重复审查，达到可安全部署的程度即可。

本文件是当前 agent 审查流程的入口。与旧计划、工程记忆或通用 skill 中的审查轮数、全量重审、人工逐步确认要求冲突时，采用本文件。功能验收标准、真实测量结果和板卡操作范围仍以对应合同与用户授权为准；历史失败和未测项照实保留。

## 1. 按改动影响决定审查量

| 等级 | 改动 | 必要检查 | 人工/独立审查 |
|---|---|---|---|
| R0 | 文档、引用、注释、状态说明、无行为变化的格式调整 | 差分、链接或格式自检 | 作者自检即可，不另起审查代理，不跑产品全套测试 |
| R1 | 不改变硬件控制和证据判定的局部功能修改 | 对应功能测试及受影响回归 | 作者自检；遇到实质疑点再请他人核对 |
| R2 | RF/PL 控制、初始化/收尾、数据有效性谓词、寄存器位语义、安装切换、RTL/时钟/引脚 | 问题复现、相关回归、关键禁止状态反例 | 常规差分由**主代理**做一次增量审查并留 REVIEW 记录（可合并规格/实现/质量结论）；**仅关键大阶段**（新候选身份、安装/切换/回滚、跨设备联调里程碑、发布）另交**独立 Codex** 做一次增量审查 |

- **2026-10-19 用户明确要求（覆盖此前"关键差分一律交独立 Codex"）**：独立 Codex 审查成本过高，只在**关键大阶段**交付 Codex 审查；日常/增量差分由**主代理**审查即可（相关测试 + 关键反例 + 一份 REVIEW 记录，不另起审查代理、不设固定变异配额）。已经发出的 Codex 审查结论按其实际范围继续有效。
- 按实际影响分类，不因“涉及安全”或“文件摘要变化”自动提升全部工作等级。
- R2 的审查覆盖原因、行为变化、必要反例和部署注意事项；不要求为每个小阶段分别产出规格审查、质量审查、封存审查和复审的复审。
- 已有独立 APPROVED 覆盖同一差分，且实际落地源码与受审补丁相符时，复用该结论并记录对应关系。实际行为增加或改变时，仅审查新增部分。
- 换目录、打包、Git 提交前移、纯文档或行尾变化不触发重复行为审查。实际交付文件的摘要仍按真实字节生成；行尾等价性可用一次差分说明核对，不冒充旧摘要。
- 不以固定测试数量、固定变异数量、全文行号零漂移作为放行标准。不影响运行的措辞、引用和审计自述问题进入后续清单，不阻塞实验部署。

## 2. 开发版部署的必要检查

1. **知道装什么**：新候选有唯一发布身份，实际部署的源码、二进制及必要 bit/HWH 与该候选一致；记录当前回退版本。文档、旧报告和全仓库树不作为新部署的默认摘要绑定对象。
2. **改动相关测试通过**：保留问题复现和修复后结果；对本次影响范围跑回归。涉及研究帧判定时，至少覆盖真实失败帧的同 IQ 重放、受影响的有效形态和关键禁止状态；顺序相关时跑一次完整假链。未改原生代码/RTL不要求重新编译它们或重做它们的全部变异。
3. **新候选能在 ARM 运行**：对 Python/算法行为修改，核验实际候选的导入、关键计算及受影响判定；可在已声明回退计划的试部署验收中完成必要冒烟，不要求另起一轮人工审查。计算路径和依赖未变时，可引用既有性能基线并明确其版本，不为仅更改谓词强制重复长时性能战役；不能把旧性能值说成本候选的新实测。现有工具若仍要求安装前 ARM 收据，按真实输入满足它一次。
4. **安装前状态可判定**：读取当前发布、服务、存储和 RF 安全态，记录 boot_id；有真实存储错误、RF 活动异常或身份不明时先定位。读取失败不能当作通过。
5. **一次安装后独立读回**：使用已有安装器及其回退机制，另开会话核对新发布、服务和 RF 安全态。超时/失联/重启造成结果未知时，先只读确认，不盲目再装。

通过上述必要检查且在用户已授权范围内，即可部署开发版；正式数据集、真人验收、S3/S4 和完整 P1–P6 验收不是每次实验候选安装的前置条件。它们仍是相应交付声明的依据。

现有安装器/runner 的可执行校验仍须真实通过。本次流程精简不提供跳过开关，不把历史失败改为通过，也不让作者伪造旧 APPROVED 或收据。若已有工具要求一轮更完整的资格测试，当前候选运行一次满足它即可，不再叠加同范围人工审查；工具本身的后续简化另按实际代码差分处理。

## 3. 测试、证据与封存

- 每个问题只保留一份清楚的复现、修复验证、审查结论和部署收据；可用索引引用同一份材料，避免重复抄录和层层再封存。
- 源码/文档改动通常由 Git 差分和提交保存，不要求每次逐文件复制旧字节、制作单独归档证明。对真实 IQ、原始日志和已签发的收据保留原件；新增解释或新版本，不改写历史结果。
- 对新增关键禁止状态，优先写直接反例。仅当普通回归不能证明该检查有效时，做少量相关变异；不对未触及的全部模块重跑战役。
- 不直接在其他 agent 正在使用的源码上做变异；使用隔离副本。临时树不入库。
- 文档变更不使未受影响的代码审查、ARM结果、物理数据全部失效；每份证据仅证明其实际版本和范围。
- 旧封存件可能绑定了阶段外文档。保留旧件用于历史回放；新阶段只绑定必要部署输入。若必须更新正在使用的工具绑定，做一次真实迁移，不删除断言或填假摘要来消除报错。

## 4. 授权与执行节奏

- 在明确授权的一项工作包内，agent 连续完成必要的实现、相关测试、一次适用的增量审查和材料生成，不为每个命令、字段或文档修改重复询问。
- 离线读日志、诊断、准备补丁和运行相关测试无需物理派发授权。用户已经授权必要修复时，不因“不在旧物理授权范围”再要求同类离线操作逐项授权。
- 安装或有线 RF 实验以用户实际给定范围为准。未授权的物理动作不从“降低审查程度”推导出来；范围扩大或现场条件不明时再询问。
- nonce、attempt_id、授权 JSON 等由工具自动生成。接线确认只需操作者确认真实接线和时间；未改变且仍满足现有有效窗口的确认可引用，不要求为了换一个候选重新插拔线缆。
- 现有 runner 的一次性账本、时间窗口和尝试预算继续按接口执行，避免超时后的重复初始化。授权内且未产生副作用的只读预检/离线校验可修正后重跑，保存失败日志；nonce 消耗后的研究不能当成剩余次数继续重派。
- 不为本地个人工程新增威胁模型、网络身份认证、签名体系或额外防篡改审批；已有 token 不显示值即可。

## 5. 本轮 src_cfg=6 的应用

独立审查已确认：src_cfg 允许集合为 {0,2,4,6}，cap_cfg 允许集合为 {0,4}；SRC_SEL/CAP_ARM 和相关禁止位仍按合同检查。此项属于 R2。

复用 `evidence/rf-teaching/s2-headroom-src-cfg6-diagnosis-2026-10-17/review/REVIEW.md` 对既有补丁的 APPROVED。对落地后的额外改动仅做增量核对；然后完成新候选身份、必要 ARM 检查、安装前预检和一次安装读回，不重开整套规格/质量/封存审查。

当前修复改变实际部署的 Python 模块，因此要在板上验证必须部署修复后的候选。离线真实帧重放通过可以证明新判定能处理旧帧，不能证明新的 46 dB 有线研究已通过。

## 6. 单次审查 + 试部署 + 验证后保留或回滚

默认采用闭环：**一次增量审查 → 确认回退版本 → 一次试部署 → 板端有界验收 → 通过则保留，功能失败则回滚并独立读回**。完整操作见[试部署与回滚 runbook](../rf/deployment-trial-runbook.md)。

- 同一次审查覆盖实际候选差分、验收命令/成功条件、时限及回退目标。部署后的机器验收与读回不是第二轮代码审查；已有批准覆盖的部分继续复用。
- 用户可一次授权“安装 + 指定板端验收 + 失败后的既定版本回滚 + 收尾读回”。在这项工作包内连续执行，不在每个动作前重复请示。回滚不扩大 RF 次数或重新授予研究预算。
- 新入口 `scripts/rf_teaching_trial_install.sh` 将现有安装器的回滚事务延长到板端验收结束。旧安装入口保持原行为；二者选择一个执行，不能先安装一次再用新入口重复安装。
- 验收失败/超时，或最终服务/发布/RF 安全态不符合声明时，触发既有旧发布/旧 unit 恢复，再读取旧版本状态。只有读回成立才记 `TRIAL_ROLLED_BACK`；不能证实则记 `TRIAL_RECOVERY_REQUIRED`。
- SSH 丢失不终止板端 systemd 作业；只观察该作业，不重派。断电、重启、存储故障和进程被强杀不能保证自动回滚，保留 UNKNOWN/待恢复结论。
- 试部署成功必须有 `TRIAL_ACCEPTED`、最终新版本状态文件以及独立读回。基础安装的 `INSTALL_ACCEPTED` 不单独证明整个试部署成功。
- 研究指标未达标与软件功能故障分开记录。真实削顶/BER 等研究负结果是否触发版本回滚，由本次验收条件预先写明；不能为了“成功”删除负结果。
