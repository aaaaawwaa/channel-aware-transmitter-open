### ⚠⚠ 判据 3.2 的数值错了 6 倍 —— 根因已定位（16 位窗计数器溢出）

**这不是判据失败，是观测通道本身有一个可证明的缺陷。** 记录在此，因为它会传染给 C3。

`f_DATA_CLK` 的测法是：DATA_CLK 域一个 16 位自由计数器，取其在一个
`2^15` 个 FCLK0 周期（= 655.36 µs）窗口两端之差，再按
`win_cycles / 2^15 × FCLK0` 换算（`platform_rf.h:70-74`）。**计数器与差值全在 16 位里**：

```verilog
reg [15:0] win_cycles;
...
win_cycles <= dclk_now - win_base;   // axi_ctrl_v1_0_S00_AXI.v:624，16 位减法
```

窗口 655.36 µs ÷ 2^16 = **99.997 MHz 就是该通道的不模糊上限**；超过就整体折回。

本板实测 `win_cycles = 0x3333 = 13107`。**把它当作 13107 就得到 20 MHz —— 这是折回后的余数**：

```
真实边沿数 = 120.0e6 × 655.36e-6 = 78643.2  ->  78643
78643 - 65536 = 13107 = 0x3333        <- 与读到的 win_cycles 逐位相符
78643 / 655.36 us = 120.000 MHz
```

**三条独立证据都指向 `DATA_CLK = 120 MHz`，而不是 20 MHz：**

1. **折回算术**：`13107 + 65536 = 78643` 恰好等于 `120.0 MHz × 655.36 µs`。
   再往上 220 / 320 MHz 已超出 AD9361 LVDS 的 DATA_CLK 范围，故 120 MHz 是唯一物理解。
2. **`init` 自己打印的时钟链**里 RX 与 TX 两侧都有 `120000000` 一级
   （TX `960/240/120/120/120/60`，RX `960/480/240/120/60/60`）—— 那正是 DATA_CLK 域。
3. **DDS 音调的频率**（见下条）要求 DDS 的推进率是 `60 MHz = 120/2`，
   而 `rf_tx_source.v:62-71` 的 `dds_ce` 正是对 `data_clk` 做 1/2 分频
   （`strobe_cnt` 0→1→0）。**两者严丝合缝。**

> **判据 1.5 的否定性没有被这个缺陷破坏**（这一点是运气，不是设计）：
> 真时钟 120 MHz 会折回成 20 MHz，**仍然远高于 1.000 MHz 天花板**，故"有钟"照样 FAIL。
> 但通道对 **≥ 99.997 MHz** 的任何频率都不再保真 —— 若 DATA_CLK 恰为
> `n × 99.9973 MHz`（如 99.997 MHz）则边沿数折回 **0**，会**谎报 NO CLOCK**。
> 本板 120 MHz 不落在那个点上，所以 1.5 仍然有效；**换个采样率就可能失效**。

> **为什么这轮差点漏掉**：原记录用"跨重启可复现"（`20001220` vs `19999694 Hz`，差 0.006%）
> 来验证这个读数。但**复现性验证的是解码，不是量** —— 一个恒定的折回余数当然次次一样。
> 仪器证伪要证的是**量程**，不是重复性。这是"先证伪仪器"这条纪律的一个反面案例。

### ⚠ 判据 C3 的标签被这个缺陷污染了（实质结论反而更强）

C3 把 `df` 除以**固件报的** `f_DATA_CLK`，于是得到"`fs = 3 × f_DATA_CLK`"。
既然那个 `f_DATA_CLK` 小了 6 倍，**这个"3"是折回因子的产物，不是接口倍数**。真实关系是：

```
fs = 实测 df × 2^12 / phase_inc = 1872.0 kHz × 32 = 59.904 MHz  ≈ 60 MSPS
DATA_CLK / 2 = 120.0 / 2 = 60 MHz                              <- 与上式一致
```

**所以 `fs = 60 MSPS`，即 `fs = DATA_CLK / 2`** —— 与驱动回读的
`TX/RX sampling rate readback = 60000000 Hz`（判据 2.5）**独立地互相印证**。
C3x 记的"与文档的 `fs = 2 × f_DATA_CLK` 不符"也随之解释清楚：**那份文档是照着
被折回的 20 MHz 写的**；真值代入后关系是 `fs = DATA_CLK / 2`。

> **本记录的处置**：C3 与 C3x 按脚本打印的结果**照抄**（脚本的判据是测量前冻住的，
> 不因事后发现仪器有缺陷而回改），但**上面这段解释是新的、必须与它们并列**。
> 仪器缺陷是**记录下来的事实**，不是把判据改绿的理由。

> **未修**：`win_cycles` 加宽到 32 位（或把窗口缩短到 2^14 个 FCLK0 周期）属于 RTL 改动，
> 是工程主体，不在本次测试任务的提交范围内。**列为阻塞级开放项**。

### ⚠ 谐波相位无关的一项更正：DDS 音调真值

原记录（本节上一版）写"`phase_inc = 128` 时真实偏移是 `f_DATA_CLK/32 = 625 kHz`"。
**实测是 `1872.0 kHz`**，该推算已被证伪，原因有两层：它漏算了 `dds_ce` 的 1/2，
又把被折回的 20 MHz 当了真。正确式子是

```
df = phase_inc / 2^12 × (DATA_CLK / 2) = 128/4096 × 60 MHz = 1875 kHz   (实测 1872.0，差 0.16%)
```

`df` 与 `phase_inc` 的线性（C2）是在同一份捕获上测的，故这个比例常数可信。

> **衍生缺陷（已记录，尚未修）**：`scope_tx_check.py` 的 `LO_LINE_TOL_HZ = 250_000`
> 的**注释**是按计划假定的 30 MHz 写的（"half the smallest plausible sideband spacing"）。
> 判据本身仍然成立，理由是**与真值无关**的：候选表 `FS_RATIO_CANDIDATES` 的步长是
> `0.5 × (phase_inc/2^12 × f_dclk)` = `0.5 × 625 kHz` = **312.5 kHz**，而
> `250 kHz < 312.5 kHz`，故**任何候选间距都大于容差，不可能认错相邻候选**。
> 缺陷只在**依据**：注释自陈的倍数关系已被实测推翻（它假定 30 MHz，真值 120 MHz）。
> 修法：从实测值推导，不要照抄计划里的假定值。
>
> **（本行先后写过两次错话，均留档）**：最初写"250 kHz 会吞掉 312.5 kHz 的边带"
> —— 312.5 > 250，吞不到；随后又按被折回的 20 MHz 算了一遍余量 —— 那也建立在
> 错误的 `f_DATA_CLK` 上。**两次都是先有结论再找数。**

### 4.1 的量化证据：这是**载波抑制**的双边带，符合 I-only DDS 的预期

在同一份保存的真实捕获（`tmp/cap_lo80_pi128.npz`）上，围绕 LO ±3 MHz 内逐峰列出：

```
78.1280 MHz  offset -1872.0 kHz  snr 55.3 dB     <- 下边带
80.0000 MHz  offset     0.0 kHz  snr 20.0 dB     <- LO 泄漏（"载波"）
81.8720 MHz  offset +1872.0 kHz  snr 56.7 dB     <- 上边带
其余 ±3 MHz 内全部 gated 峰：6.4 ~ 13.8 dB       <- 全是噪底
```

**边带比载波高约 36 dB**，正是"I-only DDS 上变频后载波被抑制、只剩 LO 泄漏"的样子。
两个边带各比噪底高约 50 dB，**不可能是噪声**。

**同一份数据也顺便证伪了两个候选偏移**（这是判定 4.2 可信度的关键）：

```
offset ±1872.0 kHz : 78.1280 / 81.8720 MHz   snr 55.3 / 56.7 dB   <- 0.0 kHz 误差
offset  ±625.0 kHz : 79.3920 / 80.6240 MHz   snr  6.5 /  6.4 dB   <- 噪底
offset  ±312.5 kHz : 79.6640 / 80.2560 MHz   snr  7.1 /  8.7 dB   <- 噪底
```

即**真音调确实在 ±1872 kHz**，RTL 算式的预测（±312.5 / ±625 kHz）在测量上不成立。

### 4.3 的实质结论（把 3.2 的缺陷代进去之后）

脚本的标签 `fs = 3 × f_DATA_CLK` 是**折回因子的产物**。真实关系：

```
fs = df × 2^12 / phase_inc = 1872.0 kHz × 32 = 59.904 MHz ≈ 60 MSPS
DATA_CLK / 2 = 120.0 / 2 = 60 MHz      <- 与驱动回读 60000000 Hz（判据 2.5）独立吻合
```

**所以 `fs = 60 MSPS = DATA_CLK / 2`**。DDS 由 `dds_ce` 对 `data_clk` 1/2 分频后推进，
**恰好每个输出采样推进一步**，设计是自洽的。C3x 的 `DISAGREES` 由此解释：
文档的 `fs = 2 × f_DATA_CLK` 是照着**被折回的** 20 MHz 写的。

> **这一步的价值**：C3 原本只是一条"落在候选集合里"的弱判据；纠正仪器缺陷后，
> 它变成**第二条互相独立的采样率证据**（DDS 音调频差 vs 驱动寄存器回读），两者一致。

`0x10A = REG_RX1_MANUAL_LPF_GAIN`（`vendor/ad9361.h:240`）是 `0x109`
（`REG_RX1_MANUAL_LMT_FULL_GAIN`）的 LPF 半边，位于**同一条使能的通道**上。

**证据链（每条都可复核）**：

1. **trace 覆盖整个 init，不是半截。** `rf_main.c:697` 先把 `RESETB` 拉低、

   SPI 传输都在 trace 里；`platform_rf.c:177` 只在 262144 条容量上限时丢记录，
   而四条 trace 都只有约 5000 条，容量守卫不可能触发过。
2. **驱动从不写 `0x10A` 的低 5 位。** 四条 trace 里覆盖 `0x10A` 的写**只有一条**，
   且是 `vendor/ad9361.c:4006-4007` 的**读-改-写**：它设 `POWER_MEAS_IN_STATE_5`
   （bit7:5，`vendor/ad9361.h:1435`），**低 5 位 `RX_LPF_IDX_MASK`
   （`vendor/ad9361.h:1436-1437`，LPF 增益索引）原样不动**。四条 trace 的形态完全一样：
   `R 10A 58` → `W 10A 58` —— **写回去的正是刚读到的那一个字节**。
3. **复位基线做标尺**。`board_app selftest` 触发一次硬件复位
   （`vendor/ad9361.c:1002-1015`；**GPIO 复位路径不写寄存器**，所以复位在 trace 里
   根本看不见 —— 这正是必须另做实验的原因），复位后实测：

   | 寄存器 | 复位后 | 说明 |
   |---|---|---|
   | `0x109` | `0x4C` | = 全表最大索引（`SIZE_FULL_TABLE - 1` = 77-1，`vendor/ad9361.c:397`），与驱动写进去的值**恰好相同** |

   | `0x10C`（RX2，未使能） | `0x4C` | 与驱动写进去的值相同 |
   | `0x10D`（RX2，未使能） | `0x00` | **四条 trace 里从未被写过** |

   `0x10A` 复位后低 5 位是 0，而 init 过程中它早已是 `0x18`（= 24），
   而 trace 里**没有任何一条写把 `0x18` 送进覆盖 `0x10A` 的字节** —— 排除掉驱动，
   **只剩器件**。
4. **它在 init 之后还会自己变，且这一点比第 3 条更硬**（不依赖 trace 的完整性）：
   `0x109` 驱动最后一次写的是 `0x4C`，而随后 `board_app audit`（**只读**进程，
   见脚本 docstring）读到 `0x45`（冻结运行）/ `0x44`（run2）/ `0x3F`（run3）——
   **都是任何一条写都没送过的值**；`0x10A` 则是 `0x58`（冻结、run2）→ `0x56`（run3）。
   **没有写、值却变了，只能是器件写的。**
5. **对照**：RX2 是**未使能**的通道，它的孪生 `0x10C` 三轮都是 `0x4C`、`0x10D`
   从来没被写过。两个通道唯一的差别就是使能与否。
   **诚实说明**：`0x10C` 的复位基线**也是** `0x4C`，所以"RX2 静如死水"单独看
   说明不了什么；这个对照真正给的是**对比** —— RX1 动、RX2 不动。

**处置**：

* `0x109` 的豁免**保留**，理由从"板级实测（推断）"改写为上述证据链；其中第 4 条是
  **证明**，不再是"像是 AGC 干的"。
* `0x10A` **新增一条豁免，但只豁免低 5 位**：kind 用 `masked`、mask `0xE0`，
  于是驱动**确实拥有**的 bit7:5（`POWER_MEAS_IN_STATE_5`）**仍然被比对**
  （写入 `0x40`、读回 `0x40`，判 CONFIRMED），放行的只有器件自有的增益索引。
  **能少豁免就少豁免** —— 只有这个方向的改动才有资格进这张表。
* **明确不豁免** `0x10C` / `0x10D`：RX2 未使能，它们就是这条豁免的对照；
  它们要是动了，那是一个**真发现**，审计必须照报 UNEXPLAINED。
* **如实披露**：`0x10A` 是**唯一**一条只凭"活运行"证据加的豁免 —— 冻结运行把它判成
  `CONFIRMED`（`docs/rf/l2_audit_stage1.txt:224`，`wrote 58, read 58`），是 run3 才
  分叉的，条目也是那时才加的。它比另外八条**基础更弱**，理由里写明了这一点，
  而不是装作它一直在那儿。

> **一处没查清、也不假装查清的事**：`0x10A` 里那个 `0x18` 是器件**什么时候**写进去的。
> trace 里看不见 —— 它发生在器件内部，不产生 SPI 事务。能证明的是
> "**不是驱动写的**"（第 2、3 条）与"**复位基线是 0**"（第 3 条）；
> 把它归给器件是**排除法**，不是观测。所以 `0x109` 的理由里把 AGC
> 写成"从寄存器名与漂移方向读出的机制"，而不是引证。

### 三次活重跑与冻结运行的写入值对照 —— 差异 100% 由命令行解释

把四条 trace 的"最后写入值"逐地址比对（287 个地址）：

```
run3 vs run2   : 0 个地址不同          <- 同一命令行，逐字节相同
run3 vs frozen : 3 个地址不同
run3 vs run4   : 3 个地址不同          <- 与 frozen 的差异是同一组
```

`run4` 与 `frozen` 在 **287/287 个地址上写入值完全相同**，差别只在 `run2`/`run3`
多给了 `atten 0`：

| 地址 | run2/run3（`atten 0`） | frozen / run4（不带 `atten`） |
|---|---|---|
| `0x075` | `0x00` | `0x67` |
| `0x076` | `0x00` | `0x01` |
| `0x07C` | `0x57` | `0x40` |

**机制已查清（不是"读数不同"）**：

* `0x075`/`0x076` 是 **TX2 的衰减**（`REG_TX2_ATTEN_0/1`），由
  `ad9361_set_tx_atten` 一次写成 2 字节：`atten_mdb /= 250`（0.25 dB/LSB），
  `buf = {MSB, LSB}` 写到 `REG_TX2_ATTEN_1` = `0x076`，多字节**递减地址**使
  `0x075` 拿到 LSB（`vendor/ad9361.c:1601-1631`；递减规则的实证见 `_record_write`
  的 docstring）。
* 不带 `atten` 时，**1R1T 的 init 会把没用的 TX2 停在最大衰减**：
  `ad9361_set_tx_atten(phy, 89750, ...)`（`vendor/ad9361.c:5543-5545`，
  89750 mdB = `MAX_TX_ATTENUATION_DB`，`vendor/ad9361.h:2852`）→ `89750/250 = 359
  = 0x0167` → `buf = {0x01, 0x67}`。**观测到的正是 `0x01`/`0x67`。**
* 显式 `atten 0`（`rf_main.c:797-799`）把 TX2 的衰减改写成 `0x0000`，
  并置 `IMMEDIATELY_UPDATE_TPC_ATTEN`（bit6）触发更新 → `W 07C 57`；
  不带该参数时只有 `ad9361_set_tx_atten` 开头那次"清 bit6"的读-改-写 → `W 07C 40`。

所以这 3 个地址的差异是**测试命令的副作用**，既不是器件状态，也不是 RTL。
**教训**：`atten 0` 看起来像"什么都不改"，实际上它**改了 TX2 的衰减寄存器**；
凡是"默认值应该等价"的假设，都要拿 trace 逐地址对一遍才知道成不成立。

### 补：2026-09-18 两轮复核 —— 改了**九处** + 新增**一条**豁免，没有一处放宽判据

复核（一次外部评审 + 两次自查）分两轮，共改了九处、新增一条豁免。
**九处全是"让理由能被复核"**；新增 `0x10A` 那一条是唯一一次**放宽**，

| 1 | 文件头 docstring | 说"六条"是在冻结运行之后加的，而表里确实是**七条** —— 数与表不符，且恰好把 `0x0F4` 那条藏起来 | 改成 SEVEN，并注明"第七"按**加入顺序**、与列表顺序不同 |

| 8 | `0x10A` | **不是"原来有问题"，是原来根本没有这一条**：冻结运行判它 `CONFIRMED`，run3 读到 `0x56` 才变成 UNEXPLAINED | 新增，kind `masked`、mask `0xE0`：**只放行器件自有的低 5 位**，驱动的 bit7:5 仍被比对（见「`0x109`/`0x10A`」一节） |

这类条目**只能靠"它到底触发没有"来抓**，读理由是读不出来的：两条的理由都写得很像回事。

* 第 2 条是**拿理由去对冻结运行自己的输出**抓到的（那份输出就在仓库里，写着 `CONFIRMED`）。
* 第 3 条是**算出来的**：把 `EXEMPT` 的地址集合与 trace 实际写过的地址集合求交 ——

  **这个求交现在是一条常备检查**：第四轮（run4）测完又算了一遍，9 条豁免全部命中，
  没有新的死条目。

> 重跑了一次活审计**（run3、run4），因为 `reason` 字符串本身就是脚本输出的一部分 ——
> 改了脚本不重跑，产物与它自称的生成脚本就对不上。

## 本次记录**不**证明什么

* **不证明 PLL 锁定。** 判据 2.3 是寄存器自洽，不是测量。
  **但这一点现在有了旁证**：4.1/4.2 在 RF 口上测到了一条比噪底高 50 dB、且频率随
  `phase_inc` 严格线性的音调。**一个没锁定的 LO 不可能搬移出一条这么干净的单音** ——
  这是"LO 在工作"的**测量证据**，比寄存器回读强。仍不写 PASS，因为它不是 2.3 的判据。
* **不证明 TX FIR 已启用。** 驱动报了 `ad9361_validate_enable_fir: Invalid ...`。
* **不证明镜像抑制 / 正交校准正确。** 驱动报了 3 条 `Unhandled case ... tx_quad_calib`。
  **本轮只测了频谱位置与幅度差，没有测镜像抑制比**，所以那 3 条告警的后果仍未量化。
* **不证明 77 条 `DECLARED-WEAK` 的写入真的生效** —— 写 0 盲区，如实列出。
* **不证明 `f_DATA_CLK` 这个观测量是对的** —— 它在**量程上**有缺陷（16 位折回，
  见 Step 6），真值 120 MHz 被报成 20 MHz。**判据 3.2 的字面（"非 NO CLOCK"）成立，
  但那个数值已被证伪。**
* **不证明 TX 数据通路（`phy_tx`）的时序余量**。本轮证明的是"器件能发出这个音调"，
  不是"PL→AD9361 的接口在 60 MSPS 下无亚稳态"。那需要眼图/ILA，未做。

### 与上一版的差别（一句话）

上一版的结论是"控制面成立，**但没有观测到任何 RF 波形**"。本版把最后那半句去掉了：
**RF 口上确实有一条被测量到的、随 `phase_inc` 线性移动的边带对**（4.1–4.5 全 PASS）。
同时本版**新增一条**上一版没有的否定结论：**观测通道 `f_DATA_CLK` 的量程坏了**。

## 过程中的六个失误（留档）

**一、对 `0x07C` 的推断过度自信。** 我在 Step 8 的中途根据 init trace 推断该豁免理由
是"bit 6 自清"，并**预测回读会是 `0x00`**。**实测是 `0x17`** —— 预测错了。bit 6 自清
是对的，但把它当成整个字节的解释是错的：低位由器件维护。若按那个理由写豁免，
**就会把"低位为什么变"这件事连问都不问地抹掉** —— 正是本轮已经被咬过两次
（`0x016` / `0x00A`）的同一类缺陷。教训：**证明了一个机制，不等于证明了解释是完整的。**

**二、冻结的审计输出漏抄了第一行。** 我造 `docs/rf/l2_audit_stage1.txt` 时把列表的

段落的一部分。后果是**产物自相矛盾**：文件头写"287 distinct addresses"、底部摘要写

（**衰减 10 dB 那一次**的 init trace）第 5049–5054 行，连 `W 074 00 28` 都是真的
（多字节地址递减，故 `0x074=00`、`0x073=28`）。**它唯一的缺陷是没写来源文件**，
而那个文件**一直不在本仓库里**，所以读者无从复核。

但更该记录的是**两次错误的"查证"**：

1. 一次外部评审的结论是"这些行在任何保留下来的 trace 里都不存在"。**错** ——
   `R 07C 17` / `W 07C 17` 在当时的 trace 里就在（第 5039–5047 行）。
2. 我把范围缩到"`W 074 00 28` 只出现在**手写的** fixture `review6_trace.txt` 里"。**也错** ——
   那条 trace 一直在板子上，只是**从未取回本机**。

**两次都栽在同一件事上：我在"本地已有的文件"里找，而"板子上还有别的 trace"这件事
从来没被排除过。** 说"这个证据不存在"之前，先要证明**搜索范围是完备的**。

而这段摘录真正的缺陷在另一处：同一个 reason 字符串里写着低位"`0x00` → `0x17` → `0x01`"
——**`0x01` 任何产物都不支持**（三条活读是 `0x17`/`0x17`/`0x00`）。它只出现在脚本自己的
`reason` 里，是**自我引用**。已从脚本和记录里删除。**这与 0x109 是同一类缺陷：
理由里写着一个读者无法复核的数。**

**六、我把 `atten 0` 当成"什么都不改"，于是 run2/run3 的 trace 与冻结运行不可比。**
run2/run3 的 `init` 命令行里我加了 `atten 0`（当时觉得是"把状态摆到确定值"）。它**不是**
无操作：`ad9361_set_tx_attenuation` 会把**两个通道**都写一遍（`rf_main.c:797-799`），
而 1R1T 的 init 本来会把没用的 **TX2 停在最大衰减**（`vendor/ad9361.c:5543-5545`，
89750 mdB = `MAX_TX_ATTENUATION_DB`）。于是那两轮的 trace 在 `0x075`/`0x076`/`0x07C`
三个地址上与冻结运行不同 —— 而我当时只把它记成"写入值不同"，**没有问为什么**，
也没意识到它与命令行有关系，直到 run4（不带 `atten`）的写入值与冻结运行**全等**，
差额才被定位到参数上。

**教训**：**"默认值"和"显式设成默认值"不是一回事**，判断两个运行是否可比的唯一办法是
**把 trace 逐地址对一遍**（正是这一对才把事故定位出来的）。这也正是一条更早的教训的
另一面：只写"写入值不同"就等于把差异解释完了，读起来像"两种运行本该一样"。
