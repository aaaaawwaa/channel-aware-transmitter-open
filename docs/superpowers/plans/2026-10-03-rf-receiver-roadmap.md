# RF接收总体开发路线

**2026-10-04方向调整：** 用户选择教学演示＋环境诊断、BPSK必交、QPSK条件扩展、建议人工确认。当前执行路线以[新总体Plan](2026-10-04-teaching-environment-roadmap.md)为准：S0收尾→S1真实星座/记录→S2限定窗口环境诊断→S3人工建议。下文多速率/RRC优先路线保留为历史长期规划，不再是下一阶段默认任务。

> 状态：2026-10-03路线基线。用户要求先总结、再建立总体plan及方向，后续按里程碑推进。M0–M3是已有证据；M4发布993ffe21已安装，新自动验收通过，真人功能待确认；M5以后是规划，不因列入路线就视为已实现或已授权新硬件/空口操作。

**目标：** 以现有AC820/AD9361有限IQ链路，完成可在板屏操作、能解释同步与误码、保留真实证据的已知数字信号接收演示；随后扩展工况及QPSK，再迁移到有参考的天线接收。

总体顺序：先闭合一条可用的接收路径，再扩展算法支持域，最后扩展物理环境。每阶段都有入口、产物、验收、失败处理；不能只用“代码写完”关闭里程碑。

## 路线选择

| 方案 | 收益与代价 | 选择 |
|---|---|---|
| 先BPSK板屏完整链路，再工况/调制扩展 | 先交付能操作和测量的功能，及时验证异步、过期、停止与发布问题 | 主线 |
| 先同时实现BPSK/QPSK/QAM/RRC，再统一接UI | 算法覆盖更快，但难拆分真实失败且可用交互推迟 | 暂不采用 |
| 先改天线和LNA，再优化分类/解调 | 场景接近实际，但缺型号/频段/参考源，不能分清算法与射频问题 | 放在参考条件就绪之后 |

## 里程碑与完成标准

| 阶段 | 工作范围 | 进入条件 | 完成标准/证据 |
|---|---|---|---|
| M0 基础链路 | 已有控制/安全/发布 | 已完成 | 最近可靠发布与实际关闭/watchdog证据，保留历史 |
| M1 采集分析 | 已有真实IQ、基础分析、UI | M0 | 捕获/取消/失效、原始IQ和metadata、有限实板及原生产真人证据 |
| M2 CNN识别 | 已有冻结有线模型 | M1 | 官方固定数据门禁、ARM数值/资源、生产草稿限制；仅限定有线范围 |
| M3 BPSK首轮算法 | 已有3MHz RECT有限接收 | M1；不依赖CNN预测 | 独立数学/负控、ARM、3会话30ON+3OFF、明确BER分母；已完成 |
| M4 BPSK板屏完整链路 | RX配置、worker、生命周期、UI、版本发布及真人验收 | M3冻结算法；继续用户已确认的有线路线 | 新软件回归、板端同输入与实际UI回调实采、关闭读回、实体触摸清单通过；详见独立实施计划 |
| M5 BPSK支持域与抗扰 | 先RECT2/3/5MHz，再RRC0.35，再频偏/相位/定时扰动 | M4功能验收；每子阶段先定义支持域与判据 | 每新增单元格分别冻结数据/参数、算法回归、ARM预算和新实测；未通过只保留实验能力 |
| M6 QPSK | 相位歧义、符号到比特映射、独立参考与BER | M5至少目标速率/成形验证完成 | 先单工况，再扩大；分开报告符号/比特错误，参考不进入同步，板屏与原BPSK回归通过 |
| M7 已知信号天线基线 | 独立已知信号源、频段/馈线/天线记录及背景对照 | 实物资料、已知参考源、适用接收域就绪；至少M4完成 | 新场景会话分组数据、同域同步/BER与背景拒绝、输入/削顶与稳定性记录；有线成绩不替代空口成绩 |

M5顺序固定为三个子里程碑：M5a多速率RECT → M5b匹配滤波RRC → M5c已定义扰动下的鲁棒性。每个子里程碑只改变明确因素，不同时混入新调制、独立设备、空口和协议帧。后续正式门槛在各自设计文档中先声明，再采独立验收数据；不能把M3的30帧当作所有新域的验收。

M6先做QPSK，QAM16/QAM64是条件扩展。QAM需要明确幅度/增益归一、映射和质量口径，另立设计；不因CNN能分类就宣称能接收或计BER。

M7是迁移路径，不强制等所有M5/M6单元格完成：只有目标来波与已验收支持域匹配时才可执行。天线型号、工作频段、馈线、已知信号源可以提前准备。外接LNA的加入依照可测弱信号需求及电平预算，不能用ADC码值变大当改进。CRC/协议帧、流式DMA/连续接收和自动识别符号率属于另一个项目入口，当前4096点快照不能宣称完整连续数字接收机。

## M4的交付批次

| 批次 | 交付 | 完成后能验证什么 |
|---|---|---|
| A | 显式RX接收配置、后台调用、冻结结果与身份 | 当前帧如何得到同步/BER；不继承TX/CNN配置 |
| B | 生命周期失效、板屏设置/状态/BER显示 | 配置修改/取消/停止/断连/过期后旧BER不显示为当前值；绘制不阻塞 |
| C | 新软件契约、隔离导入、打包/回退 | 新算法确实随发布安装；旧可靠release仍可校验和恢复 |
| D | 板端实采、实体真人交互与交付 | 脚本与现场按钮产生同一可信结果，端到端时延独立测量 |

**M4关闭条件：** A–D都完成；A/B/C通过不算“已完成真人验收”。算法纯计算P95≤200ms是旧M3目标；M4另测端到端，不能将92.88ms填入实体触摸时延。

## 开发管理规则

1. 每批开始保存相关文件/可靠发布hash，写明输入域、样本数量、门禁与新增文件；现有大量未提交内容不reset、不混合提交。
2. 新行为先写能暴露问题的测试；已有原始数据只作研发诊断，新正式验收必须新采并冻结声明。
3. 停止/取消优先处理，数据网络deadline仍3秒；当前控制watchdog及30秒快照有效期保持明确，状态轮询不续发射。
4. 软件改动优先复用原bit/HWH。发现确需PL/daemon改动时，先定位证据、修订影响范围和构建计划，再实施；不为了UI接入默认综合PL。
5. 阶段结束更新一份总结与收据：已完成/未完成、测试命令、实板/真人结果、hash、实际发布、失败与安全收尾。下次从这份收据继续。
6. 尚未具备条件的扩展进入待办，不进入当前验收或完成百分比。主线原则不变，局部设计可因证据修订，但修订要记录原因和重新验证范围。
