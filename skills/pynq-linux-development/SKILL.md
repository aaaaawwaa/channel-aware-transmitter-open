# PYNQ 板载 Linux 开发

先确定本次改动位于PL、PS驱动/控制、数据分析、UI还是部署层。不要把一个层面的通过当成整条硬件链通过。

## 建立实际运行基线

- 从目标工程的维护文档和发布清单找到入口；确认板型、镜像/PYNQ版本、Python解释器、bit/HWH、地址表和服务名称。设备地址与凭据由本地配置提供，不写入技能或公开收据。
- 开始板端操作前读取实际发布、服务、`boot_id`、存储健康和硬件忙闲状态。只能说明本次读回时点；历史记录不等于当前状态。
- 若有知识图谱，优先用图谱找模块和调用链；不可用时再按入口文件和文本搜索定位。

## 按问题选读

- 加载失败、MMIO恒零、BRAM错位、PS/PL时序：读[Overlay与AXI数据路径](references/overlay-and-axi.md)。
- 服务启动、远程操作、试部署、SSH失联或回退：读[Linux服务与部署](references/linux-and-deployment.md)。
- 屏幕结果、线程边界、采集身份与性能：读[界面与数据有效性](references/ui-and-data.md)。

## 关键约束

1. **同一套PL只能有一个重配置拥有者。** 已有守护进程持有Overlay时，不再从调试脚本或另一个服务调用`Overlay()`。单独实验前先按项目流程交接拥有权；只读诊断也不应隐式加载位流。
2. **bit、HWH与软件地址契约成套验证。** 同名不等于同次构建。软件未动PL时，复用已核验硬件，避免为了小改动重新综合。
3. **UI只请求动作并消费实际结果。** 草稿、已应用参数、设备回读和历史快照分开；结果失效时清除当前成功态，不能保留旧BER或旧图冒充新采集。
4. **部署结果未知先读回。** 远端持久作业可能在SSH断线后继续；不因超时再次安装或重复初始化。
5. **证据保存原件。** 日志/IQ/收据的脱敏在分享副本进行，原始摘要链保持不变。只记凭据来源或路径，不输出值。

## 开发和验证

对具体故障先保留最小复现；修改后跑对应离线/假硬件测试，涉及ARM行为时补目标机验证。构建、安装、物理实验和真人操作是不同证据层级。

复用项目已有候选、验收及回退入口。按实际影响做一次适用增量审查，引用未改变部分的既有证据；不要为文档或普通UI改动追加全仓审查、固定测试数量或重新跑整套硬件战役。

交付说明包含：实际改动层、运行版本、执行过的检查、板端动作与终态，以及尚未验证的部分。技能本身不提供额外安装、重配置或发射授权。
